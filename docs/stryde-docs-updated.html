01

Vision & origin

Stryde set out to be a Runna alternative built entirely on free-tier infrastructure — personalized marathon training without a subscription. Every training number a runner sees comes from a deterministic, testable rule engine, never from an LLM; the AI layer's job is to explain and contextualize that data, not generate it. That boundary shows up everywhere in this document, because it's the single decision the rest of the architecture is built to protect.

Target user

The founder's own training, plus a small, manually-approved cohort of technically-tolerant early testers willing to sideload an Android APK. Not built for a general/non-technical audience yet, and not iOS — though the codebase is cross-platform from day one so iOS needs no rearchitecture later.

Distribution

Android-first, direct-share APK (not a Play Store listing), gated behind a manual waitlist approval — no self-serve signup-to-access flow while the product is still being hardened.

Core architectural principle

The plan engine lib/planEngine/ is a pure, dependency-free TypeScript module — no network calls, no LLM involvement, fully unit-testable with fake onboarding inputs. An AI-generates-the-plan approach was explicitly considered and rejected: it reopens the injury risk the rule-based design exists to avoid, it's non-deterministic (can't be tested the same way), and training an AI on real published plans would conflict with the project's "self-authored knowledge base only, never scraped" rule. A cited investigation into a competitor's algorithm-only approach — physical therapists reporting real injuries traced to "algorithms accept[ing] user self-assessments uncritically" — directly shaped two concrete rules downstream: a forced easy-only intro period for unproven beginners, and measured activity data always outranking self-reported fitness.

Design language — the Ridge Echo mark and "Pre-Dawn Run"

The app icon (components/ui/BrandMark.tsx) draws the same terrain-profile polyline the Plan tab's own BlockProfile hero uses to visualize a training block's shape — traced twice, offset and faded on the first pass, solid on the second, as if the line were echoing — with a single accent dot marking the peak. The same shape doing double duty as both the app's icon and a real in-app data visualization isn't a coincidence: it's meant to read as "this app is about the shape of your training," not a generic running glyph.

Pre-Dawn / Frost / Accent

The base palette every screen builds from — a near-black ground, a warm off-white surface, and one saturated orange accent reserved for calls to action and the one thing on a screen that should draw the eye.

Contour & Success

A muted forest-green pair used for the mark's echo line and for anything meaning "done," "on track," or "healthy" — recovery legs, completed sessions, a synced connection.

Warning & Danger

Reserved strictly for things that need attention — a missed-session banner, a destructive confirm, a real error — never used decoratively.

Same core hex values light and dark — only surfaces, text, and borders reskin between the two modes (see Dark mode), so the brand doesn't shift depending on the runner's own device setting. Active Run is the one deliberate exception, permanently dark for outdoor daylight legibility regardless of the toggle.

02

Tech stack

Frontend

React Native 0.86 + React 19, Expo SDK 57 (expo-router file-based nav), react-native-maps, react-native-svg, react-native-health-connect, expo-location / -task-manager / -notifications / -speech / -sharing, Sentry, react-native-web (web target).

Backend

Supabase: Postgres (pgvector, pg_cron, pg_net extensions), Auth, Storage, Edge Functions (Deno). RLS on every table. No custom server beyond Edge Functions.

AI & external services

Gemini Flash (primary generation + embeddings) + Groq (fallback generation), pgvector (semantic search), Tavily (live web search), Open-Meteo (race-day weather), Google Maps, Firebase Cloud Messaging (push), Sentry (crash reporting).

Every external service is named explicitly to the user in-app (privacy-policy.tsx) — nothing is a silent third-party dependency.

03

System architecture

The client never talks to a custom server — every read/write goes through Supabase directly (Postgres via @supabase/supabase-js, RLS-scoped by the caller's own JWT) or through one of four Edge Functions for anything needing a secret or an LLM call.

Navigation & auth gating

Expo Router's file-based routing splits into an (auth) group (sign-in/up, forgot-password), an onboarding/ group (6 steps), a 5-tab main shell (tabs)/, and 12 pushed top-level screens. A single AuthGate in app/_layout.tsx runs three sequential checks on every navigation: signed-out users get bounced to sign-in (except the auth group and the privacy policy, reachable pre-account); signed-in-but-not-approved users get bounced to a waitlist screen; approved users get bounced back into the tabs unless they're inside one of the explicitly exempted top-level screens. Every new top-level screen this project has ever added needed its own entry in that exemption list — a recurring gotcha called out repeatedly across the implementation logs.

Production build: EAS environments, and a genuine blank-screen bug

The first real production Android build (an internal-distribution APK for direct-share sideloading, not a Play Store store build) surfaced a config gotcha that a dev-client build never exercises: EAS's build profiles (development/preview/production in eas.json) are a separate concept from EAS-managed environments, which only auto-resolve to "production" when a profile's distribution is "store" — this project's production profile uses "internal", so it silently fell through to the "preview" environment (zero configured env vars) until "environment": "production" was set explicitly. A release-type build also enables R8/ProGuard minification for the first time ever on this codebase, since every prior build had been a dev-client build that loads JS live from Metro and never exercises it.

Real bug — a permanently blank screen with zero diagnostic signal

Roughly ten hypotheses were tested and ruled out in sequence — missing EAS env vars (a real, separate bug, fixed but didn't resolve this), the Sentry Metro/config plugin, R8/ProGuard, a stale AsyncStorage state, an Expo Router patch-version mismatch, EAS's build-fingerprint cache — before real on-device evidence (adb was blocked by a Windows Firewall issue the entire time, so the working technique was temporary on-screen debug overlays, hot-reloaded through the existing Metro connection) isolated the actual cause: AuthContext's initial supabase.auth.getSession() call could, intermittently, never settle at all — not reject, not resolve, just hang, with loading stuck true and hasActiveGoal stuck null forever. No thrown exception (nothing for Sentry to capture), no rejected promise — a native-crash-indistinguishable blank screen with genuinely nothing to go on until the overlays made the hang visible. Fixed with a .finally()/finally{} guarantee around both the initial session check and the auth-state-change listener, plus an independent 4-second timeout forcing font-loading to stop blocking the splash screen either way. The precise root cause of why the promise hung was never conclusively identified — it stopped reproducing once the fix landed — so this is "confirmed the symptom is gone across several cold launches," not "found the exact mechanism," and worth watching for recurrence.

05

Plan generation engine

A pure, deterministic, dependency-free module (lib/planEngine/) — no Supabase, no network, no LLM. It takes a GoalInput and returns a GeneratedPlan; persisting the result and building live historicalContext from real activity data is the calling code's job, never the engine's own.

Periodization model

Four phases in fixed order — base → build → peak → taper — sourced from Pfitzinger-style periodization research, not placeholder guesses.

PhaseLength
Base~25% of total weeks (floor 1)
BuildWhatever remains after the other three are subtracted (floor 1)
Peak2 weeks if total ≥ 16, else 1 (+1 for long ultra plans)
Taper3 weeks if total ≥ 14, else 2 (+1 for long ultra plans)

Peak and taper are deliberately fixed, not proportional to plan length — "a 5-week taper is never appropriate regardless of plan length."

Below the structural floor of 5 weeks, generation refuses outright. Between the floor and the recommended minimum, a plan is still built — just flagged with a schedule-feasibility warning rather than blocked.

Pace & volume math

Pace-zone trust chain (each tier only used if the one above is absent): a prior real race result → an explicit target time (capped if unrealistic, below) → a calibration race via Riegel's formula → experience-level default bands.

Riegel's formula:  T2 = T1 × (D2 / D1)^1.06

Marathon/ultra correction (Riegel underestimates long-distance time):
  ×1.03 base
  ×1.02 extra if the calibration race was ≤10km (large distance gap)
  ×1.08 extra on top for ultra goals

Feasibility cap: a requested target time faster than 93% of the
evidence-based prediction is overridden by the evidence-based pace,
with a warning attached to the plan.

Weekly volume progression — a "3-up-1-down" cycle: three weeks of +9% growth, then a cutback week at 72.5% of that cycle's peak, capped overall at 1.6× the starting weekly volume.

Real bug — the compounding-decay cycle

Each new cycle's growth must compound from the previous cycle's peak, not from the cutback week that preceded it. Growing off the cutback dip instead nets 1.09³ × 0.725 ≈ 0.939 per 4-week cycle — net decay every cycle instead of progress. Invisible to short unit tests (which only ever exercised 1–2 cutbacks); caught only by running the actual CLI tool against a realistic 26-week plan and noticing the peak volume come out "absurdly low" (17.8km/week instead of the expected 24km/week cap). Fixed by tracking the last cycle's peak separately. The team's own stated lesson from this: run the thing end-to-end and eyeball a number against intuition — green tests on a short scenario aren't sufficient for compounding math.

Session distribution

Three lookup tables, keyed by training days/week and phase: a base table (favors tempo), a hard table (introduces intervals, used build/peak/taper), and an ultra table (80/20-principle, minimal tempo, never interval). The long run always lands on the user's chosen day; everything else is spread by even step-spacing so hard sessions aren't clustered by construction.

Real bug — uncapped easy days

An "easy" day absorbs whatever weekly volume the long/tempo/interval sessions didn't use. Previously uncapped, a low training-days-per-week plan could dump 55–70% of an entire week's volume into one easy run — often bigger than that week's own long run, and frequently the plan's very first scheduled session. Fixed with a hard cap: no easy run may exceed 65% of that week's long-run distance. Leftover volume beyond the cap is simply dropped — the weekly total becomes a soft target, not an exact quota to force-fit.

Interval structure is a real warmup/reps/recovery/cooldown shape (added as a follow-up once Active Run's live guidance for interval days turned out no more specific than any other run type) — rep distance scales by phase (600m build/taper, 1000m peak), recovery is 50% of rep distance, and rep count is derived from the remaining "hard" time budget, clamped 3–12 reps.

Adaptive adjustment — proposed, never applied automatically

Two or more missed sessions (excluding rest/race days) in the trailing 7 days triggers a banner offering to regenerate the plan from today forward, at a volume the runner can actually sustain right now — computed from their real trailing-14-day logged average, not the original self-reported starting mileage ("exactly the number that led to the plan being too aggressive to keep up with in the first place"). Race day, distance, and experience level are untouched — only the ramp restarts, gently. Declining sets a 7-day cooldown before re-prompting. The banner's own code comment is explicit: "Never auto-applies anything — this only ever proposes, and only acts on an explicit tap."

Plan history — nothing is ever deleted

Regenerating a plan sets is_deleted=true on the superseded row and inserts a fresh one, rather than overwriting in place — a partial unique index enforces at most one current plan per goal while allowing unlimited historical ones to accumulate. A day already lived through under an old plan stays visible on the calendar even after an edit, sourced from the superseded plan's own session rows rather than vanishing.

06

Tracking & activity logging

Manual logging

Only distance and duration are save-blocking — RPE, notes, heart rate, and elevation are always skippable, behind an expandable disclosure. A logged activity that's short of a linked session's target distance stays linked but doesn't flip that session to "done" — the same "does this still meet the target" check runs on create, edit, and delete, so session-completion state always reflects what's actually still logged.

GPS tracking

expo-location at Balanced accuracy, polling every ~4 seconds or 10 meters moved. Two independent noise filters run before a point is ever recorded:

  • Accuracy-radius rejection — any fix reporting worse than 30m accuracy is dropped outright, not averaged in. A stationary phone's network-based position estimate can wander tens of meters between reads; accepting it would sum that wander straight into distance.
  • Plausible-movement rejection — a fix implying faster than 8 m/s (~2:05/km, faster than any realistic sustained run) since the last accepted point is rejected too, catching what the accuracy check alone misses.
Real bug — GPS glitched even standing still

Neither filter existed on first real-hardware test; distance/pace summed raw GPS wander directly. Fixed by adding both filters above, plus a pace ceiling (readings implying slower than 30:00/km show "--:--" instead of an absurd number like "8435:04").

Recording is offline-first — only the final save on Stop needs a network call, and a failed save queues locally (AsyncStorage) with automatic retry the next time the Track tab regains focus, showing "this run is saved on your device and will sync automatically."

Active Run & voice coaching

Tapping Start speaks a full heads-up line first, then — only once that finishes, via expo-speech's own onDone callback rather than a guessed delay — a plain 5-second countdown plays with voice and the on-screen numeral moving together. An earlier 30-second version (silent until only the final 5 seconds were spoken) was shortened per direct feedback; a first sync fix (Speech.stop() before every spoken number) resolved the drift but read as a jarring cutoff, so the real fix sequences the two phases instead of racing them. During the run, a pure distance-based state machine tracks which interval leg (warmup/rep/recovery/cooldown) the runner is in and fires a one-time transition line the instant it changes, plus a rotating motivational line roughly halfway through any leg long enough to matter.

Scripts are AI-generated once per session (Gemini/Groq, same provider pattern as the coach) and cached permanently on the session row — never regenerated after. A deterministic, fully offline fallback script is built synchronously at run start so the countdown always has something to say immediately, then silently swapped for the real AI script if/when it resolves (in practice it almost always already has, since two upstream screens prefetch it ahead of "Start" being tapped). A failed AI generation is deliberately not cached, so a transient outage self-heals on the next attempt instead of permanently freezing a session on the degraded fallback.

Real bug — the live map going blank exactly when it mattered most

One array (points) was being asked to do two jobs — what the map should show, and what counts as a measured distance point — and the 30m accuracy filter that's correct for the second job was silently breaking the first: a real GPS fix could arrive and still leave the map showing nothing while it waited for one accurate enough to count. Fixed with a second field, liveCoordinate, updated on every raw fix regardless of accuracy for the map's puck/camera only, while points stays exactly as strictly filtered for distance/splits. A related design change: the GPS subscription now opens the instant Start is tapped rather than after the countdown finishes, so the countdown's few seconds become free warm-up time instead of a second, redundant cold-start right when tracking needs to begin — with isLocationActive (a first-class piece of state, not re-derived from phase at each call site) telling every screen exactly when it's safe to run its own separate GPS watch.

Health Connect (Android)

A platform-agnostic HealthDataProvider interface (already including a "healthkit" source value, unbuilt, for an eventual iOS Phase 2) sits behind Settings' connect/sync/disconnect flow. Real implementation reads ExerciseSession + aggregated Distance/TotalCaloriesBurned, filtered to running-type sessions only.

Real bug — permission granted, reads still failed

Even after independently re-checking granted permissions (rather than trusting the request call's own return value) and re-initializing the native client on every sync (it isn't persisted across app restarts), the exact same SecurityException persisted. Root cause: Android 16's newer Health Connect permission model requires the app to actually target SDK 36 for a granted permission's enforcement to take effect — confirmed only after bumping targetSdkVersion and shipping a third dev-build iteration to test it.

De-duplication against manually-logged or re-synced activities is entirely the database's job — a unique index on (user_id, source, external_id) — so the sync code just catches the resulting constraint violation and treats it as an ordinary "already imported" outcome.

Gear & photos

A shoe's cumulative_distance_km is entirely trigger-maintained from linked activities (never client-writable) — insert/update/delete on activities keeps it exactly in sync, with a default 725km (~450mi) retirement threshold. Activity photos live in a deliberately public-read Storage bucket (avoids signed-URL refresh logic anywhere a photo displays), write-scoped by RLS on the uploader's own auth.uid() path segment, capped at 3 photos per activity in app code.

AI coach architecture

The most-iterated system in the project — this section covers the actual journey, not just the final shape, because the wrong turns are as informative as the destination.

The journey

  1. Original RAG — one fixed pipeline per message: an unconditional Hugging Face embedding call, a pgvector KB match, activity/plan context, and a weekly-mileage summary, all stuffed into one system prompt, one LLM call, no web access.
  2. Full agentic tool-calling — search_knowledge_base, web_search, get_recent_activities, and get_weekly_summary all became model-decided tool calls in a sequential loop. Real correctness win (web access, at last) but a real latency regression: a compound question could cost 2–3× the round-trips of the original single call.
  3. Partial rollback — KB and user-data lookups reverted to unconditional fetch (their round-trip cost was never worth the "maybe skip it" flexibility, and it put the weekly-mileage-must-match-the-chart guarantee at the mercy of the model remembering to call a tool). Only web_search stayed a real tool, gated by a zero-network keyword heuristic so it isn't even declared on questions that don't need it.
  4. The latency floor turned out to be somewhere else entirely — a from-scratch architecture review (run deliberately blind to the existing code, to avoid anchoring on it) converged on the same suspect independently: the unconditional Hugging Face embedding call itself, hitting a free inference tier with no latency SLA, to search a knowledge base of only 5 articles that doesn't need semantic recall at that size.
  5. Full-text-only architecture — KB matching moved from pgvector/embeddings to plain Postgres full-text search (no external network call at all); every independent read for a turn fires concurrently instead of sequentially; a weekly-mileage number is template-substituted after generation instead of trusted to the model; a live factual bug (confusing a race's registration-announcement date with its actual date) led to differentiating how much reasoning effort the model spends per call. Correct for a 5-article corpus, but it gave up semantic recall entirely — a question worded with none of an article's own vocabulary could no longer match it at all.
  6. Hybrid RAG — the current architecture — with a portfolio goal specifically calling for a real, demonstrable RAG implementation rather than a justified-but-less-impressive lexical-only one, real vector search was brought back properly this time: pgvector similarity search combined with the existing full-text search via Reciprocal Rank Fusion, so a lexical match and a semantic match both count instead of picking one strategy over the other. Embeddings come from Gemini's own gemini-embedding-001 (768-dim, text-only GA model — not the newer multimodal gemini-embedding-2-preview, which is still in preview and unnecessary for text-only articles), reusing the same provider/API key the coach's chat calls already use rather than reintroducing Hugging Face or any second vendor. Queries and documents are embedded under different task_type values (RETRIEVAL_QUERY vs. RETRIEVAL_DOCUMENT) — a detail the original embedding-only implementation never used — since retrieval-tuned embedding models are trained to place the two sides close together specifically because they're tagged asymmetrically. A failed/unavailable embedding degrades to full-text-only rather than failing the request. See Hybrid RAG in detail below.

Correctness guarantees

Weekly mileage can't drift from the chart

The model never generates the current week's own number as text. It writes a literal {{THIS_WEEK_KM}} placeholder; the exact precomputed value (same Monday-start bucketing the client's own chart uses) is substituted in afterward. Not a prompt instruction the model could ignore — the model never has the opportunity to be wrong about this one fact.

Web results can't be mistaken for training advice

A hard rule instructs the model to treat web_search output as unverified third-party content, never as authoritative as the curated knowledge base, and never to follow instructions embedded in a search result.

Real bug — a press release's own publish date, mistaken for a race date

Asked when the Tata Mumbai Marathon was, the coach confidently stated a date that was actually when a government press release about registration opening was published — not the race date at all. A prompt-level warning about exactly this failure mode didn't fix it; the model even built a plausible-sounding wrong narrative around the bad date on the next attempt. The real fix was structural: Gemini's default "low" thinking effort (lowered earlier, for latency, since most tool-decision calls are mechanical) wasn't enough for the one call that actually needs to scrutinize a source, not just pick a tool. Reasoning effort now differs by call: low for a fresh decision, medium once a tool result is already in context — the common case stays untouched, and the one call that needs care gets it.

Why full-text search, not embeddings — the intermediate step

At 5–30 topically distinct articles, lexical matching finds the same things semantic search would, without a synchronous dependency on a free-tier inference API with no latency guarantee. Live-tested against the exact calibration questions used to originally tune the old cosine-similarity thresholds: full-text correctly matched the pacing question to only the Pacing article, returned zero matches for an off-topic shoe-color question (something the old approach needed a whole similarity-margin heuristic to handle), and correctly matched the knee-pain question to Injury Prevention.

Hybrid RAG in detail — the current architecture

Full-text search has a real blind spot lexical calibration questions don't surface: it can't catch a question that's conceptually related to an article but shares none of its vocabulary. Rebuilt as a genuine hybrid rather than reverting to embeddings-only — see the journey above for what changed and why.

Concrete proof, not just added complexity

The query "what should I eat before a long endurance event to avoid stomach problems" — deliberately zero shared vocabulary with the "Fueling and hydration" article — returns zero matches from the full-text-only RPC. The hybrid RPC correctly surfaces that exact article as the top result via vector similarity.

Measuring the honest cost

A same-provider A/B benchmark (scripts/benchmarkCoachChat.ts) timed a fixed set of 8 questions against the deployed function, forcing both configurations through the same LLM (Groq) so the comparison measured only the retrieval change, sidestepping a discovery made mid-benchmark: Gemini's free tier caps text generation at 20 requests per day, per project, per model — surfaced by a RESOURCE_EXHAUSTED 429 with that exact quota name once enough test traffic had run through it.

Hybrid retrieval costs roughly 11% more latency on average — the honest price of one extra sequential step (embedding the question before the KB search can run). Set against the retrieval-quality proof above, that's a measured trade-off, not a guess: measurably slower, measurably better recall. The pre-hybrid embedding column and the original cosine-similarity match_knowledge_base() function were fully replaced (384→768 dimensions, a different embedding model entirely) rather than kept alongside the new one — there was no reason to carry two incompatible generations of embeddings for the same five articles once every row got re-seeded anyway.

Database design

10 tables, all RLS-scoped to auth.uid(), with a consistent soft-delete/status-transition convention instead of hard deletes almost everywhere — training and activity history is treated as a durable record, not disposable state.

Recurring schema conventions

  • Soft-delete over hard-delete. Goals, plans, and activities all use an is_deleted/status flag rather than a real DELETE — history stays queryable even after a user "removes" something.
  • Ownership double-checked beyond RLS. Several tables carry an explicit trigger (e.g. activities_enforce_links_owner) that re-verifies a cross-reference like shoe_id or plan_session_id actually belongs to the same user — RLS alone only checks the row's own user_id, not whether its foreign keys point at that same user's other rows.
  • One active row per user, enforced by partial unique index — at most one non-deleted goal, one current plan per goal, one push token per device.
  • Grants aren't automatic. supabase db push doesn't inherit dashboard-default table privileges — a recurring class of follow-up migration across this project exists purely to patch a missing GRANT.
