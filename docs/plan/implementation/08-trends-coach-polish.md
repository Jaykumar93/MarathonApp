## Phase A1 — Dark mode

### Scope correction before implementation

The sub-plan's own text (written before implementation) characterized this as "a `ThemeProvider` swaps which palette resolves, not a call-site rewrite." That turned out to be wrong: `grep` for `^const styles = StyleSheet.create` across the repo found 34 files computing their styles at module scope, i.e. once at import time. A `ThemeProvider` that swaps an exported `colors` object does nothing for those — `StyleSheet.create()` bakes the values in before any provider could ever change them, so toggling the theme would silently do nothing on every one of those screens. Flagged this to the user via `AskUserQuestion` (full rewrite vs. "apply on next app restart" instead of instant vs. defer dark mode) before writing any code. **User chose: full rewrite now.**

### Architecture

- `lib/theme.ts` now exports only `palette` (colors identical in both modes: `predawn`, `frost`, `accent`, `contour`, `success`, `warning`, `danger`, `dangerBg`, `dangerBorder`) plus the unchanged `fonts`/`type`/`spacing`.
- `lib/theme/ThemeContext.tsx` (new) exports `ThemeColors` (the actually mode-dependent tokens — `textPrimary`, `textDim`, `textFaint`, `cardBg`, `cardLine`, `screenBg`, `inputBg`, `tabBarBg`, `missedBg`, `missedText`, `terrainFuture`, `warningBg`, `warningBorder`, `warningText`), `lightColors`/`darkColors` (values transcribed from `design.md §3`'s table; `missedText`/`terrainFuture`/`warningBorder` aren't specified there and are documented extrapolations), `lightShadows`/`darkShadows` (dark mode drops the card shadow for a 1px border instead, per `design.md §3`), a `ThemeProvider`, and `useTheme()`.
- `ThemeProvider` seeds `mode` from `profiles.theme_preference` once on profile load (never overwrites a mid-session toggle), and `setMode()` updates local state immediately while persisting to Supabase in the background — instant per `design.md §3`, no reload required.
- Conversion pattern applied to every real call site: module-scope `import { colors } from "../lib/theme"` → `const { colors } = useTheme(); const styles = useMemo(() => createStyles(colors), [colors]);`, with the `StyleSheet.create({...})` body moved into a `createStyles(colors: Colors)` function, unchanged otherwise.
- Three special cases: `app/active-run.tsx` (PRD's one deliberate "always dark" screen — imports `palette` directly, no `useTheme()` at all); `app/(tabs)/track.tsx` (real themed chrome uses the hook, but the full-bleed map-area background stays on `palette.predawn` deliberately, same "always dark" reasoning as Active Run); `components/DayDetailPanel.tsx` and `app/(tabs)/_layout.tsx` (multiple sibling components sharing one `createStyles` — each calls `useTheme()` independently, since hooks can't be shared across components).
- Self-converted 3 reference files (`Card.tsx`, `PrimaryButton.tsx`, `settings.tsx` — the last one also getting a real `Switch` wired to `setMode`, replacing the old "Dark mode · Coming soon" row) plus `app/_layout.tsx`'s provider wiring, then dispatched the remaining ~35 files across 2 background agents working from the same pattern and file-specific notes. Both batches reported clean `tsc` in their own scope.

This blocked **all** browser-based verification, not just dark mode, until fixed.
2. **`components/ui/TextField.tsx`'s input boxes stayed hardcoded `backgroundColor: "#fff"`** even after being moved into `createStyles(colors)` — the conversion agents only replaced `colors.X` references, and this was a literal string, so it was invisible to that pass. In dark mode this produced a white input box with near-white text on top (`color: colors.textPrimary`, correct for dark mode, unreadable against a white box). Fixed to `colors.inputBg`.
3. **Same class of bug, five more places**: `components/ui/ChipSelect.tsx` (unselected chip background), `components/ui/Dropdown.tsx` (closed box + option-list sheet), `components/DayDetailPanel.tsx` (`plannedCard`), `app/(tabs)/activity.tsx` and `app/(tabs)/track.tsx` (bottom-sheet modals), `app/run-summary.tsx` (delete-confirmation sheet), and `components/PlanFeasibilityWarnings.tsx` (compressed-timeline/goal-adjusted banner — was skipped by the conversion agent entirely, correctly, since it had no `colors.X` references to convert, but its hardcoded `#FFF3E0` background was still wrong for dark mode). All fixed to `colors.cardBg` (the reusable-component cases) or the existing `warningBg`/`warningBorder`/`warningText` tokens (the feasibility banner, converted to `useTheme()` for the first time). Searched the whole repo for `backgroundColor: "#fff"` / `backgroundColor: "#..."` / `color: "#..."` afterward to confirm no more of these remained outside the deliberately-fixed files (`ShareRouteCard.tsx`'s share templates, `active-run.tsx`, and genuine fixed-color-on-fixed-background pairs like white text on the accent-colored FAB).

Installed per the plan's locked-in decision, but its `LineChart`/`BarChart` both transitively import the shared `gifted-charts-core` package, whose own barrel file (`dist/index.js`) unconditionally re-exports from every chart type it ships — including `PieChart`'s `./components/AnimatedThreeDBar`, a real file on disk that Metro's web bundler nonetheless failed to resolve ("Unable to resolve... ### A percentage-height rendering trap (React Native Web)

First bar-chart attempt sized each bar via a percentage string (`height: "${pct}%"`) on a `View` nested two levels inside a fixed-height row. The percentage never resolved on web — every bar rendered at its `Math.max(4, ...)` floor regardless of its real value, which from a screenshot alone looked like "no chart is rendering" (compounded by the floating Log FAB visually overlapping the chart's right edge, briefly reading as a stray misplaced block). Inspecting the actual computed DOM (`getComputedStyle`) confirmed the bars' real heights were fine once switched to an explicit computed pixel value (`Math.max(4, (km / max) * ROW_HEIGHT)`) instead of a percentage string — nested percentage heights are the fragile part on RN Web, not percentages generally.

## Phase A follow-up — dark-mode bug sweep, calendar redesign, gear/activity polish

A second pass, prompted by live user testing of the Phase A build above rather than new scope. Two categories of work: real dark-mode contrast bugs the original conversion missed (anything using a static, mode-invariant color as if it were theme-reactive), and a genuine UX problem with the Home/Plan calendar's navigation model.

### More dark-mode contrast bugs (same root cause as Phase A1's, found by using the app)

- **Tab bar had no `backgroundColor` at all** (`app/(tabs)/_layout.tsx`) — stayed light in dark mode by simple omission. Wired `colors.tabBarBg` in.
- **Profile avatar circle disappeared entirely in dark mode** — its background was `colors.predawn`, which is the *literal same hex* as dark mode's `screenBg` (`#14161A` both). Switched it to `colors.accent` (bright orange, high contrast in both themes).
- **`PlanCalendarScroller`'s upcoming-session cells**: hardcoded `bg: "#fff"` with `text: colors.predawn` — a white box with near-black text that, in dark mode, became a white box with *still near-black* text sitting on a dark screen (illegible), and the "today" ring used `colors.predawn` as its border (invisible against a dark background). Fixed to `colors.cardBg`/`colors.textPrimary`/`colors.textPrimary` respectively.
- **`palette.contour` used as button/link text** (`PrimaryButton`'s secondary variant, `gear.tsx`'s Retire link, `SessionListRow`'s action text, log-activity's "+ Add details" link): contour measures ~1.9:1 contrast against the dark background, badly under WCAG's 4.5:1 minimum — this is what made Settings' "Sign out" and "Delete current plan" buttons unreadable in dark mode. Added a new `colors.secondaryAccent` token (same value as contour in light mode, a lightened tint — `#6BA696`, ~6.5:1 contrast — in dark mode) and moved every contour-as-text usage to it. `contour` itself is untouched for fills (session-type color coding still needs the true hue).
- **Modal/bottom-sheet backgrounds** (Activity's Filters sheet, Track's choice sheet, the delete-confirmation sheet, Dropdown's option popup) all used `colors.cardBg`, which is deliberately translucent in dark mode (`rgba(255,255,255,0.055)`) — fine for an in-flow card sitting on the solid screen behind it, but the Filters sheet floating over a dimmed backdrop became "a lot transparent," in the user's words, effectively unreadable against the busy content behind it. Added a new, fully-opaque `colors.sheetBg` token (`#22252B` in dark mode) for exactly this "elevated overlay surface" role, distinct from `cardBg`'s in-flow-card role.
- **A stray, undocumented `#B3261E` red** (used for form-validation error text in 11 files, distinct from and inconsistent with the app's actual `palette.danger` used everywhere else) unified to `palette.danger`.
- **`BlockProfile`'s planned-mileage reference line** (Plan tab's "Training block" chart) used `colors.contour` at 25% opacity — reads as a faint hint of green on a light card, reads as nothing at all on a dark one. Swapped to `colors.cardLine`, the token already tuned per-theme for exactly this "faint but visible line" role (borders, dividers) elsewhere in the app.

### Calendar redesign — month is a page, not an infinite strip

Reported behavior: sliding the day strip past the end of a month kept scrolling with no visible sign the month had changed. Rebuilt `PlanCalendarScroller` around a paged model instead of the previous "whole-plan continuous FlatList": it now renders only the currently-viewed month's days, so dragging the strip hits a hard, visible stop at the first/last day of that month. Added:
- A `‹ Month Year ›` header (previously the strip had no month label at all) with arrows that jump a whole month, disabled at the start/end of the plan's actual date range.
- A swipe gesture on the header itself for the same month-jump, alongside the arrows.
- A swipe gesture on the day-detail card below the strip (Home and Plan both) that moves the selection ±1 day, without navigating into the tapped session's own detail screen.
- Navigating to a different month now also moves the selection: to today, if that's the month being returned to, otherwise to the 1st (or the plan's actual earliest day, for a lead-in month). A day-to-day swipe crossing a month boundary is different — it keeps whatever specific day was swiped to, not a default.

Built a small `useHorizontalSwipe` hook (`lib/useHorizontalSwipe.ts`) on core React Native's `PanResponder` rather than adding `react-native-gesture-handler` — a discrete "drag past ~40px, act on release" gesture, not a true finger-follows-content slide (documented and explained to the user directly, including the tradeoff against a fuller animated-page-transition version that wasn't built). Two real bugs surfaced building this:
1. **Nested Pressables stole the touch on a real device.** The day-detail card contains its own full-card `Pressable`s (the planned/logged session rows). `onMoveShouldSetPanResponder` alone (bubble phase) let a real device's responder negotiation grant the touch to the nested Pressable first, so the outer swipe never fired — reproduced only via a genuine device-shaped test (dragging directly over the nested card, not over plain text, which is what the first browser-based check happened to do). Fixed by also setting `onMoveShouldSetPanResponderCapture` to the same check, letting the parent intercept before the child gets a chance, but only once real horizontal movement is detected (an ordinary tap on the card is unaffected).
2. **The day-strip force-scrolled on every day-swipe, not just a month change.** `PlanCalendarScroller`'s scroll-reset effect was correctly keyed on the month-filtered day array's *reference*, not on `selectedDate` — but `allDays` (the full `days` prop, computed in `index.tsx`/`plan.tsx`) was rebuilt with a fresh array identity on every render, including every `selectedDate` tick from a day-swipe. Fixed by memoizing `allDays` (guarded for `plan`/`goal` still being null, since the memo has to sit above the loading/no-plan early returns — a hook can't be called conditionally).

Also added the day-swipe to the Plan tab (it already inherited the month-paging/header/arrows automatically, being the same shared component) and proactively fixed the identical un-memoized-`allDays` pattern there before it could reproduce the same force-scroll bug.

## Phase B follow-up — first real device verification, bug fixes, polish

Phase B's code shipped untested on a real device (Open items above). This round is that actual verification - a real Google Maps key and two more EAS builds were needed along the way, and live testing surfaced several real bugs that no amount of code review would have caught, since they only manifest against actual GPS hardware, an actual Android permission model, and an actual native map surface.

**Getting a build installed at all**
- User obtained a real Google Maps API key (Maps SDK for Android is unlimited/free per Google's own billing docs, unlike most other Maps Platform APIs) and added it to `app.json`, replacing the earlier placeholder.
- First real `eas build` run from here (the user was already logged into `eas-cli`) - succeeded first try. Getting Metro connected to the installed dev-client took real troubleshooting of its own: Windows Firewall silently blocking inbound LAN connections (the network profile was set to Public, with no exception for Node/port 8081) meant `expo start --dev-client` alone never reached the phone - `--tunnel` (after installing the `@expo/ngrok` dependency it needs) was the actual fix, not a firewall change.

**Live map, once real GPS/device testing began**
- **Native view swallowed by its own clipping** - `RunMap`'s wrapping `View` (and `active-run.tsx`'s own box around it) had `borderRadius` + `overflow: "hidden"` together, a known Android issue where clipping a native surface-backed view (what `MapView` actually is) makes it silently fail to composite at all rather than just losing its rounded corners. Confirmed against Google's own Cloud Console traffic/error metrics for the Maps SDK key - real authorized requests were going out the whole time, nothing was ever visually painted. Fixed by dropping `overflow: "hidden"` from both wrappers; the rounded-card look survives from the border alone.
- **Then still invisible** - `mapPlaceholder`/`mapArea`'s `alignItems: "center"` (left over from centering the old single-line placeholder text) was overriding the default `"stretch"` cross-axis behavior, so `RunMap`'s own `flex: 1` View had no width to grow into - real height, ~zero width. Removed now that a full-bleed map is the actual child, not centered text.
- **Zoom silently skipped** - the very first `animateCamera` call (the one carrying the initial street-level zoom) could fire before the native map finished initializing and get dropped, while the "already zoomed in once" flag still flipped to true regardless - permanently skipping it for the rest of that screen's life. Gated on `MapView`'s own `onMapReady` callback instead of firing as soon as a coordinate exists.
- **Design pass**: a custom dark `customMapStyle` (POI/business/transit hidden, matching Active Run/Track's permanently-dark screens instead of Google's bright default), a custom accent-colored heading-direction puck (`HeadingPuck`, built from `react-native-svg`) replacing the default blue dot, driven by `location.coords.heading` (new optional field on `RoutePoint`).
- **Interaction**: pan/zoom are always enabled now (previously disabled during live tracking so the camera could auto-follow without a fight) - a manual drag now just pauses auto-follow instead, with a small recenter button (always visible, accent-colored while actively following, white otherwise) to jump back. Recenter always resets to street-level zoom regardless of how far you'd pinched away. The button's own vertical offset is a prop (`recenterBottomOffset`) since Track's full-bleed map has a bottom banner floating over it that Active Run's boxed map doesn't - the offset has to switch depending on whether that banner is the plain "Start run" button or the taller "Resume tracking" one, or the button ends up hidden behind whichever is showing.
- **Track's pre-run lobby had nothing to show at all** - it always passed an empty points array to `RunMap`, since no run/tracking had started yet. Gave it its own lightweight `Location.watchPositionAsync` watch (paused whenever a real run is in progress, which then shows `rt.points` - the real tracked route - instead, so the two watches never run at once).

**GPS accuracy - the first time this pipeline ever saw real hardware**
- Distance/pace glitched wildly even standing still, once location was actually flowing. Root cause: `RoutePoint` never captured `location.coords.accuracy` at all, and the distance math summed every consecutive point with zero noise filtering - a degraded/network-based fix easily "moves" 20-50m in a few seconds purely from positioning wobble. Fixed with two independent filters in `RunTrackingContext.onLocationUpdate`, before a point is ever recorded: reject a fix outright if its own reported accuracy exceeds 30m (`MIN_ACCEPTABLE_ACCURACY_METERS`), and reject a movement if the implied speed from the last *accepted* point exceeds 8 m/s (`isPlausibleMovement`, new in `gpsStats.ts` - catches two individually "accurate enough" fixes that still drifted apart faster than a person could really move, which the accuracy check alone doesn't).
- A near-zero (but not exactly zero) recorded distance over a real time span still divided out to an astronomical, technically-correct pace ("8435:04"). `computeAveragePaceSecondsPerKm` (and by extension the "recent pace" window built on it) now returns `null` - shown as "--:--" - above 1800 s/km (`MAX_MEANINGFUL_PACE_SECONDS_PER_KM`), the same way it already did for zero distance.
- Active Run's stat row dropped `PTS` (a debug counter, not something a runner needs, whatever value it had already got used for figuring out the fix above) for `AVG PACE` (whole-run average, alongside the existing live "current pace" readout above).

**Real Health Connect sync, once a real account tried it**
- **`requestPermission()`'s own return value lied** - it reported `ExerciseSession` as granted immediately after the request, but reading it moments later still threw a real `SecurityException` for lacking `READ_EXERCISE`, confirmed live via the actual Android exception text. Switched to independently re-checking with `getGrantedPermissions()` instead of trusting the request call's own echo.
- **The native client needs re-initializing every fresh app process** - `initialize()` was only ever called from `requestPermissions()` (once, at connect time); every later sync (in particular Home's silent sync-on-open, in a brand-new process with permission already granted from a past session) needs its own `initialize()` call first or reads fail quietly. Added to `getRecentActivities()` too - idempotent, safe to call repeatedly.
- **Android 16 needed a higher target SDK** - even after both fixes above, the exact same `SecurityException` persisted on a fresh install. `expo-build-properties` had deliberately only set `minSdkVersion` (26, the floor `react-native-health-connect` requires), leaving `compileSdkVersion`/`targetSdkVersion` at Expo's own default to minimize risk. Bumped both to 36 (`react-native-health-connect`'s own documented recommendation) - Android 16's newer Health Connect permission model apparently needs the app to target it for the grant to actually take enforcement effect, even though both Health Connect's own UI and this app's own check already showed it as granted. Needed a third build to test (native config change, not JS).
- **UX gap this exposed**: once `health_data_source` was set, Settings' "Connected" used to be a static label with no way to retry if that state was ever wrong (exactly what happened above) - it's now still tappable ("Connected · Sync now"), and a **Disconnect** action was added alongside it (flips the flag back to `manual` and stops syncing; deliberately doesn't call `revokeAllPermissions()` itself, since the library's own docs advise against that as an in-app toggle - the revocation only actually applies after a full app restart, so send the user to Health Connect's own settings instead if they want to fully revoke). The sync result (imported/skipped counts, or "no new activities found") is now shown directly in the Settings card instead of only via a swallowed console warning.
- **New `HealthSyncButton`** in the shared tab header, next to the profile avatar (shows only where Health Connect is actually available) - one tap either connects-and-syncs or just syncs, depending on current state, with a result `Alert.alert()`. Replaces an initially-built "Connect Health Connect?" popup reminder on Home, which was removed once this shipped.
- **Source badge**: `ActivityThumbnail` gained a small accent-colored sync-icon corner badge for any `health_connect`/`healthkit`-sourced activity (nothing shown for a manual entry, the common case) - wired into both Activity History and `DayDetailPanel` (shared by Home and Plan), so a synced run is distinguishable from a hand-typed or GPS-tracked one everywhere a logged activity appears.

**Unrelated bugs found along the way**
- **Back/exit links sitting under the status bar** - 8 screens (`settings.tsx`, `edit-plan.tsx`, `gear.tsx`, `log-activity.tsx`, `planned-session.tsx`, `run-summary.tsx`, `share-run.tsx`, and the shared `OnboardingStepLayout.tsx`, which covers every onboarding step in one fix) used a flat hardcoded top padding instead of `insets.top + padding`. Screens confirmed *not* affected: Home/Plan/Activity (get a native header from React Navigation, which already reserves the correct space), Track/Active Run (their own back buttons already computed `insets.top` correctly), sign-in/sign-up/waitlist (centered content, no back button near the top edge).
- **Chart tooltips unreadable on mobile** - `PressTooltip`'s positioning box was stretched to exactly match its narrow parent bar/cell (`left: 0, right: 0`), leaving almost no room for the label text, which wrapped one character per line. Widened symmetrically (`left/right: -60`, `maxWidth: 120`, `numberOfLines={1}`) so it can size to its actual text while staying centered over whichever bar/cell was pressed.

## Phase C — AI Coach (RAG)

Planned via Plan Mode before any code — full architecture, schema, and sequencing in the approved plan file. Two real decisions were surfaced to the user via `AskUserQuestion` rather than picked silently: activity grounding uses **structured context (direct queries), not a second vector-search pipeline** over activities (the knowledge base is the only thing that needs pgvector — it's small and static, activities are neither); and the **five knowledge-base articles are Claude-drafted**, reviewable/editable afterward, not scraped (matches the PRD's own decision log).

**Schema** (`supabase/migrations/20260908120000_add_coach_rag.sql`) — `knowledge_base` (`embedding vector(384)`, read-only to all authenticated users, no user-facing write policy at all — only the seed script's service_role key can write it) and `coach_messages` (same `auth.uid() = user_id` RLS shape as every other user-owned table, immutable — select/insert only, no update/delete), a `match_knowledge_base(query_embedding, match_count)` cosine-similarity RPC, and an `enforce_coach_message_links_owner` trigger (same ownership-consistency pattern as `enforce_activity_links_owner`/`enforce_plan_goal_owner` from the initial schema — RLS alone only checks `user_id = auth.uid()`, not that a linked `activity_id`/`plan_session_id` actually belongs to that same user). No IVFFlat/HNSW index — the table will only ever hold a handful of articles, where a sequential scan beats an index tuned for a much larger corpus.

- **Same class of grants bug as `20260902221645_grants.sql`, hit again from the other side** — the seed script's first run failed with "permission denied for table knowledge_base" even though it authenticated with the service_role key specifically to bypass RLS. RLS bypass and baseline table `GRANT`s are two separate Postgres privilege layers, and a table created via `supabase db push` doesn't inherit `service_role`'s usual elevated privileges any more than it inherits `authenticated`'s. Fixed with a second migration (`20260908130000_grant_service_role_knowledge_base.sql`) explicitly granting `select, insert, delete` on `knowledge_base` to `service_role`.

**Seed script** (`scripts/seedKnowledgeBase.ts`, mirrors `scripts/tryPlanEngine.ts`'s dev-script pattern) — five original ~300–600 word articles (pacing strategy, fueling/hydration, injury prevention with an explicit non-medical-advice disclaimer, tapering, recovery), embedded via Hugging Face's Inference API and inserted with the service-role client. Clears existing rows first so re-running after an edit doesn't duplicate articles. `tsx` doesn't auto-load `.env` the way `expo start` does, so the script carries its own minimal inline parser.

**Edge Function** (`supabase/functions/coach-chat/`, this project's first — Deno runtime, no existing pattern to follow):
- `index.ts` builds a Supabase client from the caller's own forwarded JWT (`Authorization` header from `supabase.functions.invoke()`) — RLS applies exactly as it would for any other request this user makes, no service_role key anywhere in this function. Embeds the question → `match_knowledge_base` RPC (top 3) → structured context (the specific activity/session if `activityId`/`planSessionId` was passed, plus the user's last 10 activities) → grounded system prompt → `generateReply` → inserts both the user and assistant `coach_messages` rows → returns `{ reply, sourceActivityIds, sourceKbTitles }`. A `KB_SIMILARITY_THRESHOLD` (0.3) filters which KB matches get attributed as sources, so an irrelevant article that happened to rank third doesn't show up as a citation; `sourceActivityIds` is deliberately just the one asked-about activity (if any), not all 10 recent ones, so a reply never gets misattributed to runs it may not have actually referenced.
- `llm.ts` — the Gemini-first/Groq-fallback provider abstraction the PRD requires (`try { gemini } catch { groq }`). Both model strings were live-verified via web search immediately before writing this, since both providers' lineups move fast enough that a training-data guess would likely already be stale: `gemini-flash-latest` (a real, officially-documented alias that auto-tracks Google's current Flash release, chosen specifically to avoid hardcoding a string that goes stale) and `openai/gpt-oss-120b` (Groq deprecated `llama-3.3-70b-versatile` in June 2026).
- `embeddings.ts` — same Hugging Face model/endpoint as the seed script, deliberately duplicated rather than cross-imported (Deno can't easily import from the Node-side `scripts/` directory — two genuinely separate runtimes).
- `prompt.ts` — coach persona, KB excerpts, structured activity/plan context, and explicit hard rules: never state new specific paces/mileages as instructions (the plan owns those numbers), a brief non-medical-advice disclaimer on injury/pain-adjacent questions (PRD §7 — handled by LLM instruction, not app-side keyword matching, since the LLM judges "injury-adjacent" far better than a keyword list could), concise/conversational answers.
- Deployed via `supabase functions deploy coach-chat`. End-to-end validated with a direct curl call against the live deployed function (a real user JWT obtained through the password-grant `POST /auth/v1/token` flow) before building any UI on top of it — deliberately testing the riskiest layer first. Used a real injury-adjacent question ("I twisted my ankle... should I still go for my long run?") specifically to validate the hard-rule prompt instructions in one shot: confirmed the disclaimer was present and no specific pace/mileage was invented, with Gemini answering directly (no Groq fallback triggered). Confirmed via a direct `coach_messages` query afterward that both the user and assistant rows landed correctly, with `source_kb_ids` populated only on the assistant row.

**App side**:
- `lib/data/coachMessages.ts` — `getCoachMessages(userId)`, plain RLS-scoped select. No insert function here by design; the Edge Function is the only writer.
- `lib/coach/askCoach.ts` — thin wrapper over `supabase.functions.invoke("coach-chat", ...)`.
- `app/(tabs)/coach.tsx` (full rewrite) — a real chat screen: `FlatList` message list (user bubbles right-aligned/accent, assistant left-aligned/card-styled, `borderBottomRightRadius`/`borderBottomLeftRadius` "tail" corners), a multiline `TextInput` + send button with a loading state, and reference chips under a reply — a new small `components/ui/ReferenceChip.tsx` (confirmed `Badge.tsx` wasn't reusable, it's a fixed numeric-count pill with no label/press support). Historical messages loaded from `coach_messages` only carry `source_kb_ids` (article ids), not titles — resolving those back to titles would need a join the app doesn't do anywhere else, so only a freshly-received live reply (which already has `sourceKbTitles` from the Edge Function's own response) shows KB-article chips; both live and historical messages show a tappable "View source run" chip when a source activity exists. Reads `useLocalSearchParams<{ activityId?, planSessionId?, prefill? }>()` to pre-fill (never auto-send) the input when arriving from an entry point — that context then stays attached to every message sent during the same screen visit, not just the first, so a follow-up question keeps the same grounding.
- **Entry points**: a small chat-bubble icon added next to "Planned vs. actual" in `run-summary.tsx` and "Workout breakdown" in `planned-session.tsx` (same header-row-with-icon layout `run-summary.tsx`'s Route card already used for its share icon), each navigating to `/(tabs)/coach` with the relevant id and a pre-filled question.

**Verification** — `npx tsc --noEmit` and all 106 tests clean. Live-verified end-to-end in the Browser tool: existing chat history (from the earlier curl test) rendered correctly on load; sent a fresh live question ("What's a good pacing strategy for my long runs?") and got a grounded, on-topic reply with three correct reference chips (Pacing strategy, Tapering, Fueling and hydration); confirmed both entry points' `activityId`/`planSessionId`/`prefill` params correctly pre-fill the input without auto-sending. Grepped `lib/coach/`, `lib/data/coachMessages.ts`, and `app/(tabs)/coach.tsx` for `createPlanWithSessions`/`updateGoal` — no real import, only a comment referencing them by name (the safety boundary the plan called for structurally, not just by prompt instruction).

## Phase C follow-up — UX round, blunt QA pass, and the 6 bugs it found

**UX round** (user feedback after first live use): `prompt.ts` tightened to short/plain replies with bullets+**bold** for genuinely multi-part answers instead of dense paragraphs (rendered by a new `components/ui/CoachMessageBody.tsx`, a small hand-rolled parser rather than a markdown dependency); `components/ui/CoachChart.tsx` (new) draws a compact pace-line/mileage-bar chart under a reply, computed client-side from real activity rows via the same `lib/trendsStats.ts` functions the Trends tab uses — picked by a keyword regex on the question (`PACE_RE`/`MILEAGE_RE`/`PROGRESS_RE` in `coach.tsx`), never by the LLM; a cycling "thinking steps" label replaces the bare spinner while a reply is in flight; `coach_messages` gained a `conversation_id` column (`20260908152113_add_coach_conversation_id.sql`) plus a "New chat"/History toolbar and per-conversation delete (`20260908152738_allow_coach_message_delete.sql` — the one deliberate hole in the table's original "immutable, no delete policy" design).

**Blunt QA pass**: a general-purpose agent was dispatched specifically to read the whole stack and live-test it, briefed to be critical rather than diplomatic. It found 6 real bugs (not just rough edges) - all fixed same-session, each deployed and live-verified individually before moving to the next:

1. **Chart/reply mileage mismatch** - the LLM computed "this week" as a rolling 7-day sum from raw activity JSON, while `CoachChart` buckets by calendar week (Monday-start, `lib/trendsStats.ts`). The two would name different numbers for the same question. Fixed with `supabase/functions/coach-chat/weeklySummary.ts` (new) - a Deno-side mirror of the same Monday-start bucketing (duplicated, not imported - same "two runtimes" reasoning as `embeddings.ts`), computed from a dedicated 28-day-window query (not the existing 10-row-capped `recentActivities`, which would have silently under-counted a busy month) and handed to the LLM as an explicit table it's told to quote rather than re-derive.
2. **Anti-hallucination was inconsistent, and had already produced emoji + ungrounded praise in this account's real history** ("you've kept those short, sharp race-pace efforts in the mix 🎉"). Fixed with an explicit hard rule requiring any "how's my training going" answer to cite a real number from the weekly-totals table or say plainly that the data doesn't support an opinion, plus an unambiguous "no emoji, ever, no exceptions" rule (the old one was phrased as a style preference, not a hard rule).
3. **No multi-turn memory - every message was an isolated single-shot Q&A wearing a shared `conversation_id` as a costume.** Verified live before the fix: "what did I just ask you about?" got "You asked what you just asked about." Fixed by fetching the last `MAX_HISTORY_MESSAGES` (10) rows for the conversation and threading them into both providers as real turns (`llm.ts`'s `HistoryTurn[]` - Gemini's `contents` array with `assistant` mapped to its own `model` role, Groq/OpenAI-shape `messages` array unchanged). Re-verified live: the same follow-up now correctly resolves against the prior turn.
4. **Reference chips were noise when live and gone on reload.** Two separate fixes: (a) the original single fixed `KB_SIMILARITY_THRESHOLD` (0.3, later 0.5) couldn't work at all - measured directly against the live corpus, a clearly on-topic question ("my knee is sore") scored only 0.379 while a clearly off-topic one ("what color shoes should I buy") still scored 0.292, so no fixed cutoff separates the two. Replaced with a relative-margin rule (`KB_MIN_SIMILARITY` 0.3 floor + the top match must beat the runner-up by `KB_MIN_MARGIN_OVER_RUNNER_UP`, 1.25x) and citing only the single best match instead of up to 3. (b) `coach_messages` gained a `source_kb_titles text[]` column (`20260908161009_add_coach_message_source_kb_titles.sql`), denormalized alongside the existing `source_kb_ids` specifically so a reloaded conversation can still render its citation chip without a join. Both re-verified live: the knee question now correctly cites "Injury prevention," and the chip survives a full page reload.
5. **"Ask Coach" was invisible on every one of this account's 5 real logged runs** - the only entry point in `run-summary.tsx` lived inside the "Planned vs. actual" card, which only renders when `activity.plan_session_id` is set; all 5 real runs on the QA test account are manual/unplanned. Fixed by moving to a single always-visible "Ask the coach about this run" row (icon + label, not the icon-only button flagged separately as a discoverability rough edge) right under the stat row, with prefill text that adapts based on whether a plan session exists.
6. **Stale context on a second "Ask Coach" visit** - `contextRef`/the prefilled input were seeded once from `useLocalSearchParams` via `useState`/`useRef` initial values; since the Coach tab stays mounted (no `unmountOnBlur`), a second visit with a *different* run's id silently kept reusing the first one. Investigating this live surfaced a second, worse instance of the same class of bug: even on a genuine first-ever visit with real entry-point params, the mount effect unconditionally loaded "your most recent conversation" and displayed it, so only the input got the right prefill while the visible history was a wrong, unrelated past conversation. Fixed both: a `useFocusEffect` now re-applies context when the incoming `activityId`/`planSessionId` differ from what's already applied, and the mount effect skips auto-loading history entirely when arriving with entry-point context (an "Ask Coach" visit means "start fresh about this," not "resume whatever I was last discussing"). Re-verified live via real in-app taps (Coach tab, showing an old conversation → Activity → a real run → "Ask the coach about this run") - lands on a genuinely empty state with the correct prefill, not the stale thread.

`npx tsc --noEmit` and all 106 tests stayed clean through every fix; each of the 6 was deployed and live-verified individually (not batched) before moving to the next.

## Phase C follow-up 2 — chart iteration, and two more bugs found while fixing a third

**Chart iteration** (three rounds of direct user feedback on `CoachChart.tsx`): first pass added a real x-axis (week date under each bar/point) and y-axis (min/max value) so the chart's own "this week: 0km" caption couldn't read as contradicting a tall bar for a *different*, past week - immediately hit real overlap bugs of its own (a stacked two-line "date" + "full range" label collided with its neighbors even on a wide desktop viewport; switching mileage's axis from flexbox cells to the same absolute-positioned technique the pace chart used, plus a distance-based label picker (`pickLabeledIndices`, always first/last + a middle label only if it actually clears a minimum pixel gap from both) fixed it, since the pace chart's real data points sit at their true chronological week position, not evenly by array index - a runner with only 3 logged weeks clustered at the *end* of the 8-week window would otherwise still get 3 overlapping labels). Second round: the user found the axes themselves added more clutter than clarity and asked to remove both entirely, keeping only the tap/hover tooltip - `CoachChart.tsx` reverted to just title + bars/line, with the week date moved back into the tooltip label text (which briefly reintroduced the exact truncation problem the axis had been solving, since `PressTooltip`'s bubble was capped at one line / 120px). Third round: user asked for the tooltip specifically to show the value and the full week range on two separate lines ("6 Aug - 12 Aug" style) - `PressTooltip` extended to allow a `\n`-separated two-line label (`numberOfLines={2}`, taller anchor offset, wider `maxWidth`) - additive change, `TrendsView`'s own existing single-line callers are unaffected. Also added in this round: `PressTooltip` gained `onHoverIn`/`onHoverOut` passthrough (react-native-web fires these from real mouse events, a no-op on touch), and `CoachChart` tracks a shared `activeKey` so a bar/point highlights (a white outline ring on a bar, an enlarged glowing dot on the pace line) on hover as well as press - verified real hover only works after confirming the emulator's `mobile` viewport preset deliberately disables it (matching a real touchscreen having no hover concept), not a bug.

**Two more real bugs**, found chasing a QA-flagged "lost input on failed send":
1. **A failed send silently discarded whatever was typed** - `coach.tsx`'s `handleSend` cleared the input immediately, with no restore on failure, and left the optimistic user bubble sitting in the thread with no reply and no error marker on it. Fixed: the pending bubble is rolled back and the text is restored to the input on catch, so a retry doesn't mean retyping the question.
2. **Entry-point context (`activityId`/`planSessionId`) was still being re-attached to every message for the whole screen visit**, including an unrelated follow-up question asked after the original topic - wasted tokens and a plausible source of the model getting weirdly anchored. Fixed: context is now only sent on the message that actually mints the conversation (`conversationId` still `undefined` at send time); later messages in the same thread rely on real multi-turn history (Phase C follow-up 1's fix #3) for continuity instead.
3. **Found live while verifying fix #1**: a malformed `activityId` crashed the entire request with a bare `"Unknown error"` - reproduced directly via a raw fetch to the deployed function. Root cause was two independent bugs: (a) the catch-all `e instanceof Error ? e.message : "Unknown error"` silently discarded the real message on any Supabase/Postgrest error, since those are plain objects, not `Error` instances; (b) `body.activityId`/`planSessionId` were passed straight into Postgres queries and inserts with no validation, so a non-UUID string threw a raw "invalid input syntax for type uuid". Fixed both: the catch-all now also checks for a plain object with a string `.message`, and a new `UUID_RE` normalizes `activityId`/`planSessionId`/`conversationId` once at the top of the handler - an invalid one is now just treated as absent instead of crashing the request. Re-verified live: the same malformed request that used to 500 with "Unknown error" now returns a normal 200 reply, ungrounded to any specific run as expected.

`npx tsc --noEmit` and all 106 tests stayed clean throughout; every fix in this round was deployed and re-verified live (including one bug reproduced directly via a raw `fetch` against the deployed Edge Function, bypassing the UI, to confirm the exact before/after response).

Per-run only, per the sub-plan's own scope note (bulk export is an explicit fast-follow-only-if-time item, not core scope - the PRD gives no bulk-export detail to build against). Researched the existing route/splits data model first (a dispatched Explore agent): `activities.route`/`activities.splits` are untyped jsonb columns, cast to `RoutePoint[]`/`Split[]` (from `lib/gpsStats.ts`) by callers defensively (`Array.isArray(activity.route) ? (activity.route as RoutePoint[]).filter(...) : []` - the exact pattern `share-run.tsx` already uses, reused as-is). No existing GPX/TCX/export code anywhere in the repo, and no `expo-file-system` dependency yet.

- **`lib/export/types.ts`** - `ExportActivity` (name, activityType, startTime, distanceMeters, durationSeconds), a narrow local type rather than importing `ActivityRow`, matching `lib/activityStats.ts`'s established "no data-layer coupling" convention.
- **`lib/export/xmlEscape.ts`** - the one shared helper both serializers need (predefined-entity escaping), everything else hand-built via template strings rather than an XML-builder dependency - both schemas are small and fixed, same reasoning `CoachMessageBody.tsx` gives for hand-rolling its own markdown parser instead of adding a library.
- **`lib/export/gpx.ts`** - `serializeGpx(activity, route)`, GPX 1.1, one `<trk>`/`<trkseg>` (no pause/resume segments are tracked separately - matches how this app actually records a run).
- **`lib/export/tcx.ts`** - `serializeTcx(activity, route)`, TCX v2 (Garmin Training Center XML), one `<Lap>` covering the whole run. `Sport` is always `"Running"` - checked `lib/sessionTypes.ts`'s `ACTIVITY_TYPE_OPTIONS` first and confirmed every activity type this app logs is a running variant, so no cycling/swimming mapping logic was worth writing.
- Both pure, no Supabase/expo-file-system/expo-sharing imports - tested in `lib/__tests__/gpx.test.ts`/`tcx.test.ts` (12 tests: structure, lat/lon/elevation/time rendering, name-escaping, empty-route edge case, TCX totals matching the real activity fields).
- **UI**: wired into `share-run.tsx` (the natural existing screen - already fetches the `ActivityRow` and computes `route` for the image-share flow), a new "Export run data" section with GPX/TCX buttons, shown only when `route.length >= 2` (same threshold `run-summary.tsx`'s Route card already uses). `expo-file-system` added as a new dependency (`npx expo install`, resolved `~57.0.6` for this SDK) - verified via live web docs lookup (this repo's `AGENTS.md` explicitly warns Expo's API surface moves fast) that SDK 57 uses the new class-based `File`/`Paths` API, not the deprecated `FileSystem.writeAsStringAsync` one. Native path: `new File(Paths.cache, filename).write(content)` then `Sharing.shareAsync(file.uri, { mimeType, dialogTitle })`. Web path (also verified via docs: `expo-sharing` can't share local file URIs on web at all): a plain `Blob` + anchor-download fallback, gated by `Platform.OS === "web"` - both to give web users something functional and, more immediately, so this project's web-based dev/preview testing workflow could verify the feature at all.
