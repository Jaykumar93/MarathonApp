## 1. Two scope questions resolved before writing any code

Every prior task was verified live via the Browser tool's web preview. Task 6 broke that pattern in two distinct ways, both raised with the user via `AskUserQuestion` before starting rather than discovered mid-build:

1. **GPS/maps are native-hardware features** - `expo-location` and `react-native-maps` don't meaningfully work in a browser. User chose: build the full native flow, verify via `tsc`/tests/code review here, they test real GPS behavior on their own Android device.
2. **`react-native-maps` specifically needs a custom dev build** - unlike `expo-location` (works fine in plain Expo Go), a config-plugin library like `react-native-maps` renders nothing at all in Expo Go; it needs `npx expo run:android` or an EAS development build, neither of which exist yet for this project (Task 8 is where the first real build was planned). Building the map now would mean *nothing* in this task could be tested today, including the non-map parts. User chose: build GPS tracking, distance/pace/splits, and the Pace Band UI now (all Expo-Go-testable), defer the map itself.

## 2. Pure GPS math, kept dependency-free and unit-tested

**`lib/gpsStats.ts`** (no expo-location/supabase import, same reasoning as `activityStats.ts`/`timeFormat.ts`): `haversineDistanceMeters`, `computeRouteDistanceMeters`, `computeSplits` (per-km, interpolating the exact timestamp at each km boundary rather than bucketing whichever GPS point happens to land nearest it - a ~10m-interval trace rarely lands exactly on a km mark), `computeElevationGainLoss` (sums positive/negative altitude deltas separately, skipping points with no altitude reading rather than treating a gap as a 0m dip), `computeAveragePaceSecondsPerKm`, and `computeRecentPaceSecondsPerKm` (a 60s rolling window - the whole-run average barely moves late in a long run, which isn't what "current pace" means to someone actually running).

Tested against a straight-line route along the equator, where haversine distance is *exact* (`R × Δlat` in radians, not an approximation) rather than testing the formula against itself - `lib/__tests__/gpsStats.test.ts`, 12 cases. Suite: **68 tests** (66 + these, activityStats already accounted for the two before).

## 3. Data layer extended, not replaced

`lib/data/activities.ts`'s `CreateActivityInput` gained `startTimeIso` (a GPS run knows its exact start instant, unlike a hand-typed Task-5 entry which only ever had a plain date), `elevationLossMeters`, `splits`, `route` - no migration, `activities.route`/`.splits`/`.elevation_loss_meters` all already existed from the Task 2 schema. `source` stays `"manual"` for GPS runs too - per PRD §6.4, `source` distinguishes health-platform-synced activities from app-recorded ones, not hand-typed from GPS-tracked; a GPS run is recognizable by having `route`/`splits` populated.

**`lib/data/pendingActivities.ts`** (new) - an `AsyncStorage`-backed offline queue, per PRD §6.5's "queue locally and sync once reconnected". Recording itself already needs no connectivity (GPS updates come from the device, not the network); the only place a network call happens is the final save on Stop. `createActivity()` is tried immediately; on failure the full payload is queued locally instead of losing the run, flushed next time the Track tab regains focus (`useFocusEffect`) - a natural "user's back in the app, maybe back online too" moment, not a background poll.

## 4. `app/active-run.tsx` (new)

Permanently dark (`colors.predawn`) regardless of the app's own still-Task-8-deferred light/dark setting, per the PRD's Active Run styling note. States: `requesting-permission` → `running`/`paused` → `saving` → (navigates to `run-summary` on success, or an inline "saved on this device, will sync automatically" screen on save failure).

- `Location.requestForegroundPermissionsAsync()` on mount; a clean, on-brand permission-denied screen (not a raw error) if declined.
- `Location.watchPositionAsync({ accuracy: Balanced, timeInterval: 4000, distanceInterval: 10 }, ...)` per PRD §6.5's exact tuning, appending points to local state.
- A `setInterval` tick drives the elapsed-time display independently of GPS callbacks (a run shouldn't look paused just because the last GPS fix was a few seconds ago); Pause/Resume properly accumulate elapsed time across segments via refs (not state, to avoid resubscribing the watch on every render) rather than naively diffing from a single start timestamp.
- **Pace Band, scoped down**: the mockup's full mile-marker visualization is inherently route/map-adjacent (markers plotted along the path), so it's deferred alongside the map rather than built as a disconnected number. What shipped instead: current pace (the 60s rolling window from `gpsStats.ts`) plus a plain "Goal 7:41/km (+12s)" ahead/behind line when the run is linked to a planned session with its own target pace.
- On Stop: computes final distance/splits/elevation via `gpsStats.ts`, saves via `createActivity` (falling back to `pendingActivities` on failure), and marks the linked planned session completed (the existing Task-5 `createActivity` behavior, unchanged).
- Registered in `app/_layout.tsx` (`AuthGate` exception + root `Stack`, `presentation: "fullScreenModal"`) - the same new-top-level-route checklist item every prior task has hit.

## 9. Route visualization and a shareable route card - without waiting for the map

The user asked for a route picture per logged run. Raised via `AskUserQuestion` first since "png or svg" genuinely implied two different builds: a real static map image from a third-party Static Maps API (needs an API key, a paid quota, a live network call), or a lightweight line-art rendering of the route's own shape with no basemap at all. User chose the latter - which, unlike the live map, needs **no dev build**: `react-native-svg` was already installed (Task 4), so this is fully buildable and testable in Expo Go right now.

- **`lib/routeShape.ts`** (new, pure/tested - `routeShape.test.ts`, 6 cases): `projectRoute(points, width, height, padding)` - an equirectangular-style local projection (longitude scaled by `cos(latitude)` so the shape isn't stretched away from the equator), uniformly scaled and centered into a fixed box. Guards the zero-span case (a perfectly straight out-and-back, or a single point) without dividing by zero. Same dependency-free pattern as `gpsStats.ts`/`intervalProgress.ts`.
- **`run-summary.tsx`** gained a "Route" card (only rendered when `activity.route` has 2+ valid points - manually-logged runs never have one) - an SVG polyline through the projected points plus start (green)/finish (dark) dots and a small legend, using the exact same `Card` styling every other section on this screen uses.
- **Follow-up ask**: a shareable version of that route - "route at top, stats at bottom, full card, pick a design, share it." Raised a second `AskUserQuestion` on scope specifically: a full freeform position/font/color editor vs. a handful of pre-built templates to pick between. User chose **presets** - simpler to keep looking good, and still reads as "customizing the design" without a drag-and-drop canvas to build and maintain.
  - **`components/ShareRouteCard.tsx`** (new) - three fixed templates (`classic`, `overlay`, `bold`), each a genuinely different layout/color treatment (light card with the route on top and a stat row below; the route filling the whole card with a dark gradient scrim and white stats overlaid at the bottom; a dark "poster" style with one hero distance number) rather than three palette swaps of the same layout.
  - **`app/share-run.tsx`** (new route, reached via a small share icon in run-summary's Route card header) - previews the selected template, a pill row to switch between the three, and a **Share** button pinned to the screen's bottom edge (same reachability reasoning as every other pinned button this session). ## 10. Activity name, description, and up to 3 photos - new Storage infrastructure, editing, and a redesigned share card

The user asked for a name, description, and photos on every saved activity, with photos optionally usable as the share card's background. Two decisions raised via `AskUserQuestion` first: **up to 3 photos per run** (not just one), and for GPS-tracked runs specifically, **collect name/description/photo before Save, on Active Run's own finished screen** (not after, on Run Summary) - manual entries get the same fields added directly to their existing form instead, since they aren't time-pressured the same way.

- **Schema**: `activities.name text`, `activities.photo_urls jsonb` (migration `20260904120000_add_activity_name_photos.sql`, applied live). `notes` already existed and doubles as "description" - no new column needed for that.
- **Supabase Storage - a first for this codebase.** New public-read `activity-photos` bucket; RLS on `storage.objects` scoped by the upload path's first folder segment (`{userId}/{filename}`) matching every other table's `auth.uid() = user_id` ownership pattern, just expressed the way Storage requires it. Chose public-read deliberately (running photos aren't sensitive the way training data is) specifically to avoid signed-URL refresh logic everywhere a photo is displayed - the stored URL just works, same as any other field.
- **`lib/data/activityPhotos.ts`** (new) - `uploadActivityPhoto` (`fetch(uri).blob()` + `.upload()`, the standard Expo/Supabase pattern for turning a local `file://` picker result into upload-ready bytes with no extra file-system dependency) and a best-effort `deleteActivityPhoto`.
- **`components/ui/PhotoPicker.tsx`** (new, reused in both log-activity.tsx and active-run.tsx) - up to `MAX_ACTIVITY_PHOTOS` (3) square slots, one open "+" slot until full, `light`/`dark` variant for the two very different screen backgrounds it needs to sit on.
- **`expo-image-picker`** (new dependency, works in Expo Go, confirmed against the SDK 57 docs before writing any code per this repo's `AGENTS.md`) - `selectionLimit` set to whatever's left of the 3-photo cap.
- **`log-activity.tsx`** gained a Name field (top of the form) and the photo picker (inside the existing notes/heart-rate/elevation disclosure).
- **`active-run.tsx`'s finished screen** - was previously zero-input (stats + Save/Discard only); now a real form (Name, Description, Photos) sits between the stats and the Save/Discard buttons, so this had to become an actual `ScrollView` (was a centered, non-scrolling `View`) to avoid the keyboard/content overflow problem a form on a fixed-height screen would otherwise hit. **Default name is auto-generated, not left blank** - a second follow-up from the user ("the name are same for every day... add date and distance so it can be distinguished") after noticing every easy day would otherwise default to the identical "Easy run": the seeded default is `{session type or "Free run"} · {date} · {distance}`, e.g. "Easy run · Sep 4 · 5.0km", seeded once via a `rt.phase === "finished"` effect guarded so it never overwrites something the user already typed.
- **`RunTrackingContext.save()`** signature extended to accept `{name, notes, photoUrls}` and pass them through to `createActivity` - the offline-queue path (`savePendingActivity`) already forwards the whole input object, so this needed no separate change there.
- **`run-summary.tsx`**: photo display moved from just under the date (user: "looks weird" at the top) to the very bottom of the scrollable content, after Route/Planned-vs-actual/notes. Gained a pencil **Edit** button (top-right) that turns Name, Description, and Photos into real inputs in place - **Distance and Duration only become editable when the activity has no recorded route** (`isTracked = routePoints.length > 0`), since a GPS run's numbers come from real recorded data that would silently disagree with the stored route/splits if hand-edited; a tracked run shows a plain explanatory note instead of input boxes. Added `updateActivity()` to `lib/data/activities.ts`, mirroring `createActivity`/`deleteActivity`'s existing plan-session-completion-recheck logic: an edit that drops distance below the planned target reverts a completed session to pending (unless another still-non-deleted activity for it still covers the target), same as deleting the activity would.
- **`ShareRouteCard.tsx`** gained an optional `backgroundPhotoUri` prop - every template (not just one) can swap its plain/gradient background for the run's first photo plus a uniform dark scrim (for text/route legibility over an arbitrary photo), satisfying "give option of both" as a toggle layered on top of template choice rather than a fourth template.
- **`share-run.tsx`** - the template picker changed from tappable pills to an actual swiped paged carousel of the real full-size cards, and doubles as its own capture source: the outer box is sized to exactly one card with `overflow: hidden`, so `react-native-view-shot` capturing it only ever grabs whichever card is currently swiped into view (same clipping any paged ScrollView screenshot would show), never a mid-scroll sliver of a neighboring template - no separate hidden/offscreen capture copy needed. Added a "Use photo as background" `Switch` (only shown when the activity has photos) and a Description section (from `notes`) below the carousel, Share button still pinned at the very bottom.
- **Real layout bug found and fixed**: pinning a button to the screen's bottom edge only works if the `ScrollView` above it has `style={flex:1}`, not just a `contentContainerStyle` - without it, content doesn't actually get bounded/clipped to the available height (confirmed by inspecting the live DOM: a `ScrollView` missing this had `scrollHeight` far exceeding its own unclipped `height`), so on a short viewport the pinned button visibly sat on top of un-scrolled content instead of the content being scrollable past it. This one had gone unnoticed on `run-summary.tsx`/`planned-session.tsx` because their content happened to be short enough not to expose it; `share-run.tsx`'s taller carousel-plus-extras content is what surfaced it. Fixed in all four screens using this pinned-bottom-button pattern (`run-summary.tsx`, `planned-session.tsx`, `share-run.tsx`, `active-run.tsx`'s finished screen).
- **Verification note**: this session's Browser-tool sandbox turned out to have unreliable click-coordinate targeting for this round specifically (clicks not landing on/focusing elements despite correct on-screen coordinates) - diagnosed as a tooling limitation, not an app bug, using the same `elementFromPoint`/DOM-inspection technique that found a real bug earlier in this task (the Dropdown focus-stealing issue): confirmed the target elements were always the correct, topmost, `pointer-events: auto` element at their exact coordinates. Verified the actual edit → save → persist round-trip by focusing/typing/clicking through real DOM events via script instead of the flaky coordinate-based automation, and confirmed against the live database that the edit genuinely persisted (then reverted the test edit and the earlier synthetic route/photo/name/notes data afterward, restoring the one real activity in the account to its original clean state).
- Not verified from here (needs a device): actual photo picking from a real library (`expo-image-picker`'s native picker UI doesn't render in this sandbox), Storage upload of a real photo, and the OS share sheet.
